# Product Introduction Page Structure

## Default Story Arc

A complete technical product introduction commonly uses:

1. Cover: product name, category, and one-sentence promise
2. Presenter or credibility, when relevant
3. Agenda
4. Current problems
5. Product definition
6. Existing landscape or alternatives
7. Differentiation
8. Core concepts
9. Installation or first-use path
10. Daily workflow
11. Integrations or advanced architecture
12. Real scenarios and cases
13. Team adoption or rollout
14. Customization and extensibility
15. Closing CTA

Remove chapters that do not advance the audience's decision. Do not target an arbitrary slide count.

## Slide Contract

Every slide needs:

- One audience question
- One sentence the audience should remember
- One primary visual object
- No more than one main interaction or reveal sequence
- A clear transition to the next question

## Cover

Use the literal product name as H1. Supporting copy explains the category or outcome. Include only one subtle start affordance and one optional documentation link.

## Agenda

Group the talk into three to five chapters. Show the audience how the explanation will progress, not a long list of every slide.

## Problem Slides

Use concrete recurring failures. A vertical list works for three related problems; a comparison or sequence works when the problems build causally.

## Definition And Differentiation

Define the product in one sentence before listing capabilities. Explain its place in the system and then compare with known approaches on consistent dimensions.

## Concept Overview

Use a two-by-two or compact grid only when concepts are peers. Give each concept a stable semantic accent and a one-sentence role.

## Workflow Slides

Use the representation that matches reality:

- Steps for a simple procedure
- State machine for controlled lifecycle and recovery
- Timeline for recorded events
- Architecture graph for dependencies
- Table for comparison

Reveal one stage at a time while preserving previous context.

## Case Slides

Show starting condition, actions, user control point, output, and captured learning. Prefer real artifacts, diffs, commands, trace events, or screenshots.

## Rollout And Adoption

Use explicit stages with exit criteria. Avoid aspirational roadmaps without ownership or measurable completion conditions.

## Closing Slide

Use:

- Product name or direct invitation
- One-sentence outcome
- Runnable command or primary action
- Primary documentation CTA
- Secondary source or example CTA
- Compact author or company footer

Remove repeated feature explanation.

## Presentation Versus Reading Mode

Slidev uses a fixed presentation canvas. For public mobile reading, provide one of:

- A responsive article route generated from the same content
- A vertical overview page linking to slides
- A downloadable PDF plus accessible text transcript

Do not claim that shrinking a 16:9 canvas is responsive design.
